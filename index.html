How I run a project

The same four steps on every engagement, whatever the industry.

Discover

I sit with the client, learn the goal behind the request and work out what really needs building.

Prioritise

We rank the work by impact, agree the order together, and I turn it into a backlog.

Build

I brief developers on the goal, run sprints and daily stand-ups, and send clients a written update every day.

Release

CI/CD, test cases and a staging environment keep releases repeatable. A project document keeps handovers quick.

Project management in practice

The full project lifecycle, as I run it on live client work.

  • Initiation

    Define the goal

    I start with a technical interview and discovery sessions with the client. We agree the business goal, the scope and what a successful release looks like before any work begins.

  • Planning

    Scope, estimates, schedule

    The backlog is ranked with the client by impact and estimated in story points. I plan 1 to 2 week sprints, set milestones and release dates, and assign developers across projects.

  • Execution

    Team and client rhythm

    I run daily stand-ups with developers and a daily meeting with each client, followed by a written update. I clear blockers, brief the team on the goal behind each task and run technical reviews.

  • Monitoring and control

    Risks, changes, quality

    I track progress against milestones, raise delivery and technical risks early, and agree scope changes with the client before they affect the plan. Each sprint ends with a retrospective. When an Electron.js app failed on Ubuntu 22 because of a kernel issue, I added OS-compatibility checks to every release.

  • Closing and handover

    Release and knowledge transfer

    Releases go out through CI/CD with a staging environment and test cases. Each project has a document covering repositories, branches and who worked on what, so a developer change is covered by a short knowledge-transfer session.
